Methodology

Why rooted subplan comparison

A full query plan matching only when trees are exactly identical is too strict a criterion for evaluating a synthetic workload generator: two plans can diverge at the root (e.g. a different top-level sort or aggregation strategy) while agreeing on the vast majority of their internal join and scan structure. Rooted subplan comparison captures this partial, localized agreement.

  1. Parse the execution plan into a rooted tree

    Each plan is parsed from its indented ASCII representation into a tree of operator nodes (SEQ_SCAN, HASH_JOIN, NESTED_LOOP, AGGREGATE, …), preserving the parent–child structure implied by the tree connectors.

  2. Enumerate every rooted subplan

    Every node in the tree — not just the root — defines one rooted subplan: itself together with its entire descendant subtree. A tree with n nodes therefore contributes exactly n rooted subplans, ranging from single leaf scans to the whole plan.

  3. Canonicalize each subplan

    Each subtree is serialized recursively as OPERATOR(child₁, child₂, …), with sibling subtrees sorted lexicographically at every level before serialization. This produces a canonical string so that structurally identical subplans — regardless of incidental left/right ordering of join inputs — always map to the same representation.

  4. Form the subplan sets A and B

    The distinct canonical strings occurring anywhere in the original plan form set A; the distinct canonical strings of the synthetic plan form set B. Duplicate substructure within a single plan (e.g. two identical scans) is only counted once per set, consistent with the Jaccard set formulation.

  5. Compute intersection, union, and similarity

    The intersection A ∩ B is the set of subplans that appear, structurally unchanged, in both plans — direct evidence that the optimizer reached the same local decision. The Jaccard index |A ∩ B| / |A ∪ B| then summarizes overall structural agreement on a 0–1 scale.

Jaccard Similarity
J(A,B) = |A ∩ B||A ∪ B|

A = rooted subplans of the original plan  ·  B = rooted subplans of the synthetic plan

Worked Example
|A| (unique subplans, original)  = 24
|B| (unique subplans, synthetic)  = 21
Intersection = 18
Union = 24 + 21 − 18 = 27
Similarity = 18 / 27 ≈ 0.667

A high score indicates the synthetic query drives the optimizer to reuse the same access paths and join strategies as the original — i.e. the synthetic benchmark preserves optimizer behavior, not merely surface SQL similarity.
